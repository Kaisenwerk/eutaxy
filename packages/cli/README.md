# @eutaxy/cli

**Purpose.** The `eutaxy` command: `check`, `report`, `prover install` and `mcp`, config loading, engine discovery.

**Public surface.** `main` (the command), `runCheck`, `cloudflareRegressionTest`, the generators for the check test and Vitest config, and `checkInWorkerd` with its `CheckTransport` (the half of the check that runs inside workerd: the generated test holds only its module globs and one call to it; `workerd.ts` and `keys.ts` import nothing that needs Node). `eutaxy check <scenario.sim.ts>` writes `<dir>/.eutaxy/` (its test, config and report named by a stamp of the run, so two checks of one scenario at once never share them; `specs.ts` shared; a run removes its own files, and the directory once no run's files are left), runs the user's Vitest with the Cloudflare plugin there, reads the verdict back from the test's task meta through Vitest's JSON reporter, prints text or `--json` (`--exhaustive` runs every schedule within the bounds), writes `<name>.regression.test.ts` on a violation, and exits 0/1/2 for BOUNDED/VIOLATED/UNSUPPORTED (1 also when a spec is REFUTED). For a scenario's `specs`, it reads every spec file next to the scenario with its module into `SpecIR` on the Node side (`findSpecModules`, through `@eutaxy/prover/reader`) and writes `.eutaxy/specs.ts`, which maps each module to its specs as plain data and a lazy loader of its spec file (`specFiles`); the generated test observes the listed modules while the scenario runs, loads their spec files, and reports their spec verdicts; a listed module that is missing or whose spec file does not read exits 3. `--prover <name>` (`lean`, `smt`, or both separated by a comma) runs the `PROVEN` rung on the Node side after the check: each named engine on each observed module's source (`proveSpecs`, the engines in `provers`), folded into the spec verdicts by `aggregate`; a `CONFLICT` exits 1 like a refutation, an unknown engine name 3 (`enginesNamed`). `eutaxy report [dir]` (`runReport`) runs every spec file under the directory (default the working directory) on the Node side, with no scenario: each module and its spec file are imported in a child process of their own, started on `report.ts` itself (a process, not a worker thread: V8 on Node 24 can crash the whole process while threads share the WebAssembly code Node strips types with), where a relative import from a `.ts` file resolves as TypeScript resolves it (`./domain.js` and `./domain` find `domain.ts`) (`testModule`: the module's output goes to stderr, its state starts fresh, and a module that does not load, ends its process, or whose properties do not finish within `moduleBudgetMs`, default 60 s, leaves its properties `UNKNOWN`), the ladder starts at `TESTED` (`checked: false`) with `--seed` (default `report`), `--prover` adds the `PROVEN` rung as `check` does, and the verdicts print by module with a count, or `--json`; it exits 1 for a `REFUTED` or `CONFLICT` spec (an `UNKNOWN` fails nothing), 3 for a spec file that does not read, no spec files, an unknown engine, or a flag only `check` takes. `eutaxy prover install <lean|smt>` (`runInstall`, `installToolchain`, the `toolchains` by engine name) puts the engine's pinned release for this platform in Eutaxy's cache, where the engines look first: the file named in the engine's table (`leanDownloads`, `z3Downloads`) is downloaded from the upstream GitHub release, or from a mirror URL or an offline directory holding it under the same name (`--from`), into `<cache>/downloads`, its SHA-256 is checked against the table before anything is unpacked (a mismatch, a failed download, an archive without the executable or one with an entry escaping the directory installs nothing and leaves no download behind), it is unpacked into `<cache>/toolchains/<name>/<version>` (`archive.ts`: a `tar.zst` read as it decompresses with Node's zstd, a `zip` through Node's inflate, a single top-level directory flattened) beside a marker file written last, and deleted; a toolchain already there is reported and not downloaded again; `--json` prints the result; exit 0, or 3 on an error. Nothing is run by the install. `report --goals` (with `--prover lean`) writes each module's open Lean goals beside its spec file as `<spec>.goals.lean` (`WrittenGoal`; the engine's `goals`, rendered by `@eutaxy/prover-lean`'s `renderGoals`; no open goal removes a goal file left behind) and lists them in the report (`goals` in the JSON); `ReportOptions.only` keeps one module, the one whose spec file it names. `check --json` names the regression test it wrote (`regressionTest`). `eutaxy mcp` (`serveStdio`, `handleLine`, the `tools`) serves the Model Context Protocol over stdio, one JSON-RPC message per line, logs on stderr, until stdin closes: both the stateless `2026-07-28` revision (`modernVersions`; version and client capabilities in each request's `_meta`, `server/discover`, results with `resultType` and the server's identity) and the `initialize` handshake of `2025-11-25` and before (`legacyVersions`); tools `check`, `report`, `goals`, `prove` and `prover_status`, each running the command with `--json` and returning the report as structured content beside its text (a verdict is a result; a command that could not run or an argument that does not fit is `isError`; an unknown tool or method a protocol error); requests are served one at a time; the server's version is `eutaxyVersion` (`version.ts`, kept in step by the release tooling). On any command a value flag given without a value is an error.

**May import.** `@eutaxy/spec`, `@eutaxy/core`, `@eutaxy/engine`, `@eutaxy/cloudflare`, `@eutaxy/prover`, `@eutaxy/prover-lean`, `@eutaxy/prover-smt`, `@eutaxy/report`, `@eutaxy/aws`. Only these are declared in `package.json`, and
pnpm links only declared workspace dependencies, so an import of any other
package does not resolve. The project references in `tsconfig.json` mirror the
list; a test keeps the two in sync with the design.

**Phase.** v0.4 onward; v0.11 (`prover install`), v0.12 (`mcp`, goal files). See `docs/design.md` and `docs/roadmap.md`.
