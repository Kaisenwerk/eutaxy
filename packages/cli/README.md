# @eutaxy/cli

**Purpose.** The `eutaxy` command: `check`, `report`, `prover install` and `mcp`, config loading, engine discovery.

**Public surface.** `main` (the command), `runCheck`, `cloudflareRegressionTest`, the generators for the check test and Vitest config, and `checkInWorkerd` with its `CheckTransport` (the half of the check that runs inside workerd: the generated test holds only its module globs and one call to it; `workerd.ts` and `keys.ts` import nothing that needs Node; `workerd.ts` and `regression.ts` are the subpaths `@eutaxy/cli/workerd` and `@eutaxy/cli/regression`, which the published `eutaxy/cloudflare` entry takes instead of this index, so a scenario-only user loads neither the spec reader nor the compiler). `eutaxy check <scenario.sim.ts>` writes `<dir>/.eutaxy/` (its test, config and report named by a stamp of the run, so two checks of one scenario at once never share them; `specs.ts` shared; a run removes its own files, and the directory once no run's files are left), for a scenario with `callee()` steps (`callees.ts`: the scenario module is imported in Node for them when its source mentions one; each callee's wrangler config is read as JSON or JSONC by `wrangler.ts`, the one reader of configs and their bindings that `draft` uses too, so both agree on which classes are SQLite-backed and which resources two configs share) also a main module re-exporting the caller's exports and the callees' Durable Object and Workflow classes under qualified aliases, named as the plugin's `main` in a config whose miniflare options add the callees' resources under `<name>/<binding>`, while the test imports the callees' modules and passes them with their names and the aliases of shared resources (the same database, bucket or KV namespace in both configs, a Durable Object class bound across scripts with `script_name`: the caller's binding to a callee's class is redirected to the generated alias class, and the callee's binding of a shared resource is an alias of the caller's), and otherwise names the scenario's `worker.entry` as the plugin's `main` (the scenario module is imported in Node for every check, and a scenario that does not load there without callees falls back to the config's `main` with a note on stderr), so the Durable Object and Workflow classes that run are the entry's; replaces every service binding of the caller's config in the isolate with a function that is never called (`miniflareOptionsSource`' `callerServices`: the platform answers a scripted binding and hosts a callee, so the Worker a binding names need not exist); points the plugin at the wrangler config the scenario names (`worker.config`, which need not sit beside it; `--wrangler` replaces it); runs the user's Vitest with the Cloudflare plugin there, reads the verdict back from the test's task meta through Vitest's JSON reporter, prints text or `--json` (`--exhaustive` runs every schedule within the bounds), writes `<name>.regression.test.ts` on a violation, and exits 0/1/2 for BOUNDED/VIOLATED/UNSUPPORTED (1 also when a spec is REFUTED). For a scenario's `specs`, it reads every spec file next to the scenario with its module into `SpecIR` on the Node side (`findSpecModules`, through `@eutaxy/prover/reader`) and writes `.eutaxy/specs.ts`, which maps each module to its specs as plain data and a lazy loader of its spec file (`specFiles`); the generated test observes the listed modules while the scenario runs, loads their spec files, and reports their spec verdicts; a listed module that is missing or whose spec file does not read exits 3. `--prover <name>` (`lean`, `smt`, or both separated by a comma) runs the `PROVEN` rung on the Node side after the check: each named engine on each observed module's source (`proveSpecs`, the engines in `provers`), folded into the spec verdicts by `aggregate`; a `CONFLICT` exits 1 like a refutation, an unknown engine name 3 (`enginesNamed`). `eutaxy draft [config]` (`draft.ts`: `draftScenario` reads a JSON or JSONC wrangler config and scans the Worker module's source, with the modules it imports by relative path, as text; `renderDraft` writes the scenario with the invariants and the drive's events as TODO holes; `runDraft` prints it or writes `--out`, never over a file) drafts a scenario: D1, Durable Object, R2 and Workflow bindings become setup steps, a service binding a `callee()` when a wrangler config of that Worker's name is found under the directory (else a scripted `service()`), the drive a queue consumer, a Cron Trigger, an Agent's route or `fetch()`, the hosts fetched by literal URL the externals, and unmodelled bindings and guesses notes in the file; the MCP tool `draft` returns it as data. `eutaxy report [dir]` (`runReport`) runs every spec file under the directory (default the working directory) on the Node side, with no scenario: each module and its spec file are imported in a child process of their own, started on `report.ts` itself (a process, not a worker thread: V8 on Node 24 can crash the whole process while threads share the WebAssembly code Node strips types with), where a relative import from a `.ts` file resolves as TypeScript resolves it (`./domain.js` and `./domain` find `domain.ts`) (`testModule`: the module's output goes to stderr, its state starts fresh, and a module that does not load, ends its process, or whose properties do not finish within `moduleBudgetMs`, default 60 s, leaves its properties `UNKNOWN`; `testModules` runs a few modules' processes at a time and gives their verdicts, and what each writes to stderr, in module order, holding a module's output until its turn in memory up to 1 MiB and then in a file, `held-output.ts`, and starting no module eight or more places past the earliest unfinished one), the ladder starts at `TESTED` (`checked: false`) with `--seed` (default `report`), `--prover` adds the `PROVEN` rung as `check` does, and the verdicts print by module with a count, or `--json`; it exits 1 for a `REFUTED` or `CONFLICT` spec (an `UNKNOWN` fails nothing), 3 for a spec file that does not read, no spec files, an unknown engine, or a flag only `check` takes. `eutaxy prover install <lean|smt>` (`runInstall`, `installToolchain`, the `toolchains` by engine name) puts the engine's pinned release for this platform in Eutaxy's cache, where the engines look first: the file named in the engine's table (`leanDownloads`, `z3Downloads`) is downloaded from the upstream GitHub release, or from a mirror URL or an offline directory holding it under the same name (`--from`), into `<cache>/downloads`, its SHA-256 is checked against the table before anything is unpacked (a mismatch, a failed download, an archive without the executable or one with an entry escaping the directory installs nothing and leaves no download behind), it is unpacked into `<cache>/toolchains/<name>/<version>` (`archive.ts`: a `tar.zst` read as it decompresses with Node's zstd, a `zip` through Node's inflate, a single top-level directory flattened) beside a marker file written last, and deleted; a toolchain already there is reported and not downloaded again; `--json` prints the result; exit 0, or 3 on an error. Nothing is run by the install. `report --goals` (with `--prover lean`) writes each module's open Lean goals beside its spec file as `<spec>.goals.lean` (`WrittenGoal`; the engine's `goals`, rendered by `@eutaxy/prover-lean`'s `renderGoals`; no open goal removes a goal file left behind) and lists them in the report (`goals` in the JSON); `ReportOptions.only` keeps one module, the one whose spec file it names. `check --json` names the regression test it wrote (`regressionTest`). `eutaxy mcp` (`serveStdio`, `handleLine`, the `tools`) serves the Model Context Protocol over stdio, one JSON-RPC message per line, logs on stderr, until stdin closes: both the stateless `2026-07-28` revision (`modernVersions`; version and client capabilities in each request's `_meta`, `server/discover`, results with `resultType` and the server's identity) and the `initialize` handshake of `2025-11-25` and before (`legacyVersions`); tools `check`, `draft`, `report`, `goals`, `prove` and `prover_status`, each running the command with `--json` and returning the report as structured content beside its text (a verdict is a result; a command that could not run or an argument that does not fit is `isError`; an unknown tool or method a protocol error); requests are served one at a time; the server's version is `eutaxyVersion` (`version.ts`, kept in step by the release tooling). On any command a value flag given without a value is an error.

**May import.** `@eutaxy/spec`, `@eutaxy/core`, `@eutaxy/engine`, `@eutaxy/cloudflare`, `@eutaxy/prover`, `@eutaxy/prover-lean`, `@eutaxy/prover-smt`, `@eutaxy/report`, `@eutaxy/aws`. Only these are declared in `package.json`, and
pnpm links only declared workspace dependencies, so an import of any other
package does not resolve. The project references in `tsconfig.json` mirror the
list; a test keeps the two in sync with the design.

**Phase.** v0.4 onward; v0.11 (`prover install`), v0.12 (`mcp`, goal files). See `docs/design.md` and `docs/roadmap.md`.
